# Bad-KK Report and Free Replacement Rule — CURRENT

## Purpose

Protect buyer trust while K-KUT expands across all themes.

## Core rule

If a customer reports a bad KK / K-KUT / HUG and review confirms a defect, GPM should correct or replace it free.

## Covered defects

- start too early
- start too late
- end too early
- end too late
- resolving note cut off
- musical tail cut off
- wrong section
- wrong emotional match
- audio artifact or glitch
- dead audio link
- wrong HUG delivered

## Why this matters

Owned music can still be cut wrong.

Theme population must be recursive and iterative.

Bad reports are not just complaints. They are KKr training signals and PIX-PCK control events.

## Required lineage

Every bad-KK report should connect back to:

- KK ID
- section ID
- PIX handle
- parent PIX-PCK when available
- HUG ID when available
- theme
- public HUG label
- route context
- audio URL

## Customer-facing principle

If the music moment starts or ends wrong, cuts off the resolving note, links incorrectly, or does not match the approved HUG delivered, GPM will correct or replace it at no extra charge after review.

## Internal refinement loop

Report
→ classify defect
→ review audio
→ confirm / reject defect
→ recut or retire
→ update section registry
→ update theme seed
→ replace delivery
→ feed KKr learning
→ roll up to PIX-PCK

## Release impact

A theme is not fully L4 until bad-KK report handling and free replacement workflow exist.

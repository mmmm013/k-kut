# GPEx User Partition Rules

## Purpose

Every K-KUT, HUG, TUG, GPEx, GPMx, 4PE, admin, patent, process, and growth action must identify the user arm it serves.

No page, feature, flow, or development task should mix public buyers, recipients, admin operators, business clients, partners, patent readers, and internal processor language without a clear reason.

## Core Rule

Partition first. Build second. Publish third.

Before changing a page, feature, product flow, data file, or governance rule, assign it to a primary user arm.

## GPEx User Arms

### 1. Buyer / Sender

The person choosing a kut, adding a message, and sending a HUG or TUG.

Public words for this user: kut, HUG, TUG, Keepsake Page, message, recipient, private link, delivery.

Do not show this user internal terms such as KK, mK, KPD, LLF, KKr, 4PE processor, source pool, candidate inventory, or routing logic.

### 2. Recipient

The person receiving and opening the HUG, TUG, or Keepsake Page.

This user needs warmth, clarity, privacy, and simple instructions.

Do not show this user processor, catalog, routing, fulfillment, or invention jargon.

### 3. Admin / Owner

Gregory D. Putnam as founder, songwriter, catalog owner, system owner, and final approval authority.

This user may see internal language, proof gates, source-control rules, fulfillment records, test results, and protected admin pages.

### 4. MC-BOT / Operator

The guided execution layer that helps present choices, capture intent, route safe options, and support fulfillment.

This arm may use internal rules, but must present only buyer-safe language to public users.

### 5. Partner / Community Organizer

A school, church, nonprofit, town, ministry, memorial group, event organizer, or outreach partner.

This user needs campaign-safe language, group delivery options, pricing access rules, and simple program descriptions.

### 6. Business / Process Client

A client using GPEx or 4PE as a process-control, workflow, intake, routing, audit, or production system.

This user may see process language when appropriate, but consumer HUG/KUT pages should remain separate.

### 7. Creator / Catalog Owner

A future artist, songwriter, rights holder, or catalog partner who may use the K-KUT / HUG mechanism with their own controlled works.

This user needs ownership, rights, catalog preparation, approval, and proof language.

### 8. Patent / Investor / Licensee

A legal, patent, investor, manufacturing, or licensee audience reviewing the invention, process, claims, proof, scalability, and business model.

This user may see GPEx, 4PE, KKr, KPD, LLF, processor, routing, and invention architecture language.

## Page Assignment Rule

Every route should have one primary user arm.

Public buyer routes should primarily serve Buyer / Sender or Recipient.

Admin routes should primarily serve Admin / Owner or MC-BOT / Operator.

Governance and patent documents may serve Patent / Investor / Licensee, Business / Process Client, Creator / Catalog Owner, or Admin / Owner.

## Development Assignment Rule

Every new action or development task must be labeled with:

- Primary user arm
- Secondary user arm, if any
- Public language allowed
- Internal language allowed
- Checkout impact
- Admin impact
- Recipient impact

## Doctrine

Clear user partition protects the invention and clarifies the product.

Public users get simple emotional language.

Internal users get precise process language.

GPEx growth must never blur those audiences.
